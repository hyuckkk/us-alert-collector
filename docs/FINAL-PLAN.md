# 최종 실행 계획 — 남은 3가지를 한 번에 마무리

남은 일은 셋뿐이다: ① 개인정보 이력 정리 ② 전체 검색 성능 시험 1회 ③ 소유자 전용 운영 시험. 기능 추가·반복 검증은 하지 않는다.
아래 **승인 A~D** 를 한 번에 받으면 이 순서대로 끝까지 진행하고, 중단 조건에 걸리면 그 자리에서 멈춰 보고한다.

## 0. 소유자가 먼저 할 일(10분)

| # | 할 일 | 방법 |
|---|---|---|
| 0-1 | `PRIVACY_TERMS` 입력 | Settings → Secrets and variables → Actions → New repository secret. 한 줄에 하나, 4글자 이상(번지+거리명, 가족 이름, 학교명, 텔레그램 ID, 참가 가능일). 도시 이름·우편번호 숫자만 단독은 피함 |
| 0-2 | (권장) main 보호 규칙 | Settings → Branches → Add rule `main` → Require status checks: `privacy`, `collector`, `worker` → 병합 전 개인정보 검사 통과를 GitHub 이 강제 |
| 0-3 | 3개 봇에 `/start` | @ColoradoLife_bot, @ColoradoFamily_bot, @ColoradoKids_bot |

## 1. 개인정보 이력 정리(승인 A) — 약 30분 + GitHub 지원 처리 대기

1. 진행 중인 실행이 없음을 확인하고 작업 브랜치를 push 해 둔다.
2. `scripts/history_rewrite_check.sh` 를 **그 시점 최신 브랜치**로 실행한다.
   - 비공개 백업 번들과 비공개 치환 규칙을 쓴다.
   - 판정 '통과' 여야 진행한다.
3. 같은 결과로 브랜치 5개(stage1-review, stage2-fixes, stage3-fixes, stage4-preop, stage1-structure)를 `--force-with-lease` push 한 뒤 `stage1-structure` 를 삭제한다. `main` 은 건드리지 않는다.
4. test 워크플로의 privacy 결과가 개발 모드에서 **경고 없이 통과**하는지 확인한다.
5. GitHub 지원 요청을 낸다. 옛 커밋 목록은 비공개로 첨부한다.
6. 지원 완료 연락이 오면 `scripts/check_old_commits.sh` 로 웹·API·git 세 경로를 실제 확인한다. 0건이 될 때까지 후속 요청한다. 이 대기는 2·3 단계와 병행한다.

- 중단 조건: 검사 '실패', `main` 해시 변화, 브랜치별 커밋 수 불일치, push 거부.
- 복구: 비공개 백업에서 해당 브랜치만 되돌린다(개인정보가 다시 공개되므로 비상시에만).
- 보고: 이력 검사 건수 전→후, 브랜치 끝 커밋, 지원 처리 확인 결과(개수만). 옛↔새 대응표는 공개하지 않는다.

## 2. 전체 검색 성능 시험 1회(승인 B, 유료 약 $3–6) — 약 30분

1. 이력 정리 뒤의 `stage4-preop` 에서 `ticks/fullsystem` 을 push 한다(`max=1500`).
2. 건식 실행으로 일반 수집, 키워드 검색, AI 신규 발굴, AI 추출·판정을 돌린 뒤 기준 행사 18건(+제외 13건)을 단계별로 평가한다(`eval/stages.json`).
3. 보고할 지표:
   - 단계별 발견 수, 그 단계에서만 발견된 수, 행사로 남은 수
   - 날짜·비용·연령 정확도
   - 알림 대상 수(지인 기준·소유자 기준)
   - 제외 행사 오탐 수
   - 실제 AI 사용액

- 중단 조건: 사용액이 $6 를 넘을 조짐이 보이면(`--max` 상한) 그 회차 결과만 보고한다. 재실행하지 않는다.
- 해석 한계(보고서에 명시): 추가 정보원을 기준 행사를 보고 골랐으므로 '등록 정보원' 단계 값은 낙관적이다.

## 3. 소유자 전용 운영 시험(승인 C·D) — 배포 1시간 + 3~7일

1. `stage4-preop` → main **PR** 을 연다.
   - 엄격 검사(privacy·collector·worker)가 모두 통과해야 한다.
   - 통과하면 병합한다(승인 C).
2. `deploy-worker` 가 자동 실행된다.
   - 엄격 개인정보 검사를 먼저 하고 → D1 0003 적용(기준선 '시작 대기') → Worker 배포 → 비밀값 동기화 → 웹훅 순서다.
   - 이 사이 예약 수집·발송은 준비 확인에서 건너뛴다.
3. 확인:
   - `admin status`
   - `admin baseline` 에서 `awaiting_start: true`
   - `test-send` → 3개 봇 DM 수신 → 버튼 → `clicks` 기록
4. `collect` 를 수동 1회 실행한다. 실행 보고서에서 정보원 성공률, 사용액, 알림 대기열이 모두 '요약'인지 확인한다.
5. `baseline-start`(36시간) → 다음 날 아침 요약 수신 → 기간 만료.
6. 3~7일 자동 운영한다(승인 D, 월 예산 $20 유지). 매일 확인한다.
   - 수집 성공(full 1 + light 5)
   - 감시 26시간 공백 없음
   - 사용액
   - 중복 0
   - 새 정보 없는 날 0통
   - 접수 시작·마감 ⏰

- 중단 조건과 복구:
  - 중복·오발송·한국 시스템 이상 징후가 보이면 collect·dispatch 워크플로를 Disable 한다.
  - 필요하면 `wrangler rollback` 으로 Worker 를 되돌린다.
- 예산 메모: 실운영 예상은 월 약 $45 이다. $20 에 닿으면 AI 단계는 멈추고 수집 항목은 대기열에 보존된다(증액은 별도 승인).
- 최종 보고: 운영 기간 지표, 발견율 결과, 지인 발송·예산 결정에 필요한 자료.
