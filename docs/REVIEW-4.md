필수 테스트 두 가지의 실제 시나리오:
- **1번:** outbox 쓰기를 DB 트리거로 강제 실패 → 행사도 저장되지 않음 확인 → 같은 행사 재처리 → 소유자·지인 두 사람 대기열 생성 → 각 1통 발송. 이어서 "행사는 있고 지인 몫이 없는" 이전 코드 상태를 만들어 재처리 → 지인만 생성되고 소유자는 재발송 없음.
- **2번:** A 가 꺼냄 → A 임대 만료 → B 가 새 임대로 다시 꺼냄 → A 가 `extracted` 보고 → `rejected:["q1"]`, 행은 B 의 임대·`queued`·결과 없음 그대로 → B 의 보고는 반영.

- 자녀 이름·나이·학교, 텔레그램 ID, 비밀값(토큰·키)은 어느 커밋에도 없음(형식 검사 통과).

## 4. 첫날 기준선 절차 (옛 정보 대량 발송 방지)

1. 배포 직후 `admin` → `baseline-start`(기본 36시간): 이 기간에 처음 들어온 행사는 조용히 등록.
2. 단, 곧 행동이 필요한 것만 일간 요약에 넣는다(즉시 알림 없음):
   - 3주 안에 열리거나 진행 중인 행사
   - 2주 안에 접수가 시작되거나 마감되는 행사
3. 기간 동안 `collect` full 1회 + light 몇 회가 대기열을 정리한다. 하루 처리 상한은 300건이라 남은 것은 다음 날 이어서 처리.
4. `baseline` 으로 조용히 등록된 건수와 요약 건수를 확인한 뒤 `baseline-stop`(또는 기간 만료).
5. 이후에는 정상 동작한다. 조용히 등록된 행사도 날짜·비용·접수 등 중요한 내용이 바뀌면 그때 알림이 간다.
6. 기존 규칙도 함께 작동한다. 이미 끝난 행사는 제외하고, 연도를 추정해야 하는 글 중 게시 120일이 지난 것은 지난 행사 글로 보고 제외한다(`rules.finalize`, `OLD_POST_DAYS`).

## 7. 남은 한계

- 실제 D1·실제 텔레그램 시험은 승인 전이라 아직 하지 않았다(로컬 D1 은 같은 SQLite 엔진이지만 지연·제한은 실제와 다르다).
- 임대 만료 뒤 아무도 다시 가져가지 않은 경우에도 늦은 보고는 거부한다(지시대로). 그 항목은 다음 실행이 다시 처리한다. AI 결과가 `extracted` 로 저장된 뒤라면 AI 는 다시 부르지 않는다.
- 기준선은 시간 창 기준이라, 창이 끝난 뒤 처음 처리되는 옛 항목은 정상 알림으로 간다. 하루 처리량(300건)보다 대기열이 크면 창을 48~72시간으로 늘리는 것을 권한다(최대 72시간).
- 기준 목록 30건은 초안이며 사람 확인 전이다.
